# Virtual classes

A virtual class is a scheduled room a host opens, up to fifty people join with credits or a discount code, six of
them take the stage, and the whiteboard beside the video is encrypted in the browser. This document records what
is built, what it deliberately is not, and how an operator runs it honestly.

## What the server does

| Concern | Where it lives | What the server knows |
| --- | --- | --- |
| Scheduling, price, capacity | `virtual_classes` | everything |
| Who is in the room | `virtual_class_attendees` | who, when they arrived, what they paid, their stage seat |
| Presence | `last_seen_at` heartbeat | who is currently alive, within 75 s |
| Attendance report | `virtual_class_attendees` + sessions | minutes, sessions, credits paid |
| Whiteboard | `virtual_class_board_events` | an ordered list of bytes it cannot decode |
| Chat and presence | `virtual_class_signals` | who sent what *type* to whom, never the content |
| Discount codes | `virtual_class_discount_codes` | percentage, use limit, expiry |
| Media | `internal/media` | see "The media server" below — it forwards packets and stores nothing |

## What the server does not do

- **No recording, no transcription, no mixing to disk.** A recording is a custody decision about other people's
  voices and should not arrive as a side effect of a scheduling feature. The forwarder has no write path.
- **No whiteboard plaintext.** The room key is generated by the host's browser and travels **in the join link's
  URL fragment** (`#k=…`), which no browser sends to a server. Board events are opaque ciphertext; the API
  validates base64 shape and stores it. A late joiner replays the board by asking for everything after `seq`.
- **No payment card.** A class is priced in **learning credits** only. `creditsCost: 0` is a free class. A host
  who wants money takes it through the ordinary store, not through a room fee the API has no ledger for.

## Fifty seats, and why the number is real

A peer-to-peer **mesh** costs each participant one uplink stream per peer. At fifty people that is fifty
uploads per phone, which no mobile connection carries — the old 8-seat ceiling was an honest description of a
mesh, not a policy choice.

The room is therefore forwarded by a media server (`apps/api/internal/media`, built on `pion/webrtc`):

- every participant holds **one** peer connection to the server;
- the host and up to five speakers publish; the server copies their packets to everybody who wants them;
- capacity is capped at **50** in validation *and* clamped at the door, so a row written by hand cannot admit
  the fifty-first person into a room the forwarder cannot carry.

What that costs, stated plainly:

- **Media is encrypted hop by hop, not end to end.** DTLS-SRTP protects participant → server and server →
  participant, but the server terminates both legs, so it can see the media. It does not record, and there is no
  code path that could, but that is a promise kept by the code rather than a property of the architecture. The
  whiteboard and chat keep their end-to-end property, because neither goes through the forwarder.
- **Uplink.** A full class with six publishers is roughly 6 × 400 kbit/s ≈ 2.4 Mbit/s of viewer downlink, and
  the server needs that per viewer in egress.
- **The stage is six seats, not fifty.** Fifty connections at 400 kbit/s each is more than a phone's downlink;
  a grid of fifty postage stamps is worse teaching than six faces plus a roster. Everybody else is in the room,
  visible on the roster, able to chat, and promoted into a slot when the host says so.

The connection's shape is fixed by the six stage slots: a slot holds a permanently bound audio and video track,
so promoting a speaker changes *which* publisher feeds a slot and never renegotiates anybody's connection
mid-sentence.

## The free-session limit

A free class (`creditsCost: 0`) is capped at **45 minutes**:

- at creation, a free class longer than 45 minutes is a `400` naming `durationMinutes`, and a free class with no
  stated length defaults to 45 (a paid class defaults to 60);
- at the door, `requireOpen` closes a free room whose session started more than 45 minutes ago — seating,
  joining, publishing and drawing all go through it. Merely refusing the caller would leave the seats and the
  stage open past the booking, so the class is ended and its attendance closed.

Paid classes run for the length their host booked, up to 480 minutes.

## Joining

`POST /v1/virtual-classes/{id}/join` performs everything that can race inside one transaction:

1. the class row is locked (`SELECT … FOR UPDATE` on PostgreSQL; SQLite serialises writers anyway);
2. an existing attendee row returns `200 alreadyJoined: true, creditsSpent: 0` — a double submit is not a
   second charge;
3. capacity is clamped to at most 50 and counted after the lock, so exactly one of two people takes the last
   seat;
4. a discount code's `uses` is incremented with `max_uses` in the `WHERE` clause, so two simultaneous uses of
   the last one cannot both succeed;
5. the price is charged as a **negative ledger row** keyed `credits:virtual-class:<classID>:<userID>`, which is
   also what makes the charge idempotent;
6. the host is seated on stage in slot 0; everybody else starts as `audience` with slot `-1`.

A price is never trusted from the client. The host can only change the class's own price, and only while it is
not live.

## The stage

`POST /v1/virtual-classes/{id}/stage` (host only) promotes a participant to `speaker` or returns them to
`audience`. Slots are allocated by the server from the lowest free one — a client asking for slot 3 is asking,
not deciding — and a demotion closes the participant's media session so their camera stops being forwarded
immediately rather than when the connection times out.

## Media negotiation

`POST /v1/virtual-classes/{id}/media` takes the browser's SDP offer and returns the forwarder's answer plus the
slot the server assigned. One request, one response:

- a publisher offers one audio and one video m-line to send on, then the stage's six video+audio receive pairs;
- an audience member offers only the receive pairs;
- the server's answer lines up one for one, which is why nothing is ever renegotiated.

A caller who is not seated gets `403`; the stage role comes from the attendance row, never from the request.

## Presence and attendance

A browser that crashes never sends a leave. Presence is therefore a heartbeat: an attendee is `present` while
`last_seen_at` is inside the 75-second window, and the signalling poll doubles as the heartbeat so there is no
separate ping endpoint. Attendance minutes are derived from the same rows, so the headline number in the host's
report is measured rather than asserted.

## The shareable link

A class has a 16-character slug drawn from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (32^16 possibilities, no
characters that are read aloud badly). `GET /v1/join/{slug}` is the one anonymous route: it answers what the
class is, who hosts it, how many seats it has and what it costs *before* asking for an account, and it does not
list the roster.

`joinUrl` is built from `EDUMART_WEB_URL`, so the link a host copies points at the deployment that issued it. The
host's "Copy link" appends `#k=<board key>`, which is how the board stays end-to-end encrypted while still
reachable from one shared URL.

## Consistency

`GET /v1/consistency` is the habit view: current streak, longest streak, and a per-day strip. It is **derived**
from activity the system already records — attempts started, live classes attended, credits earned — rather than
counted in a column, so it cannot drift from what happened. Days are UTC days and the payload says so.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `EDUMART_WEB_URL` | `http://localhost:3000` | Origin of join links and invitation links |
| `EDUMART_ICE_SERVERS` | one public STUN server | JSON array of iceServers |
| `EDUMART_MEDIA_UDP_MIN` / `EDUMART_MEDIA_UDP_MAX` | unset (OS picks) | UDP range pinned for the media forwarder, for a firewall that only forwards a few ports |
| `EDUMART_REFERRAL_RATES` | `10,3,1` | Commission percentage per referral level |

## NAT traversal

`GET /v1/virtual-classes/{id}/ice` returns the deployment's `RTCPeerConnection` iceServers list verbatim.

- The default is a single public **STUN** server. That gets most home networks to the forwarder.
- A deployment behind a **symmetric NAT** edge, or one whose UDP range is closed, needs a **TURN** relay. Set
  `EDUMART_ICE_SERVERS` to a JSON array including `turns:` entries with credentials to enable it.
- The forwarder itself needs its UDP ports reachable from the internet. On a host with a firewall, pin
  `EDUMART_MEDIA_UDP_MIN`/`MAX` and open that range.

## Referral levels

Commission is paid up the referral chain, one ledger row per level, each with its own rate and its own
idempotency key (`commission:referral:<orderID>:L<level>:<userID>`):

- the chain is walked from `referral_attributions` → `referral_codes.owner_user_id`, one hop per level;
- a refund reverses **every** level proportionally (`commission:reversal:<refundID>:L<level>`);
- a cycle stops the walk instead of paying around it;
- `GET /v1/referrals/tree` reports each rung's count, qualifications and actual paid commission.

Students, tutors and institutions all participate: `accountType` at signup is intent used for onboarding, and
it changes nothing about who may refer or be referred.

## What is not built

- No TURN server is deployed in this repository; only the configuration path for one.
- No recording, transcription or captions.
- No mobile video room: the mobile app lists classes and sittings and opens the link; the room itself is the web
  app, so there is one implementation of the board's key rather than two that disagree.
- The stage is six seats. Larger panels are a product change (a second stage row would double the downlink), not
  a config flag.
