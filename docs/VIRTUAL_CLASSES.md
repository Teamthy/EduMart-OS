# Virtual classes

A virtual class is a scheduled room a host opens, up to fifty people join with credits or a discount code, six of
them take the stage, and the whiteboard beside the video is encrypted in the browser. This document records what
is built, what it deliberately is not, and how an operator runs it honestly.

## What the server does

| Concern | Where it lives | What the server knows |
| --- | --- | --- |
| Scheduling, price, capacity | `virtual_classes` | everything |
| Who is in the room | `virtual_class_attendees` | who, when they arrived, what they paid, their stage seat |
| Presence | `last_seen_at` heartbeat | who is currently alive, within 75 s |
| Attendance report | `virtual_class_attendees` + sessions | minutes, sessions, credits paid |
| Whiteboard | `virtual_class_board_events` | an ordered list of bytes it cannot decode |
| Chat and presence | `virtual_class_signals` | who sent what *type* to whom, never the content |
| Discount codes | `virtual_class_discount_codes` | percentage, use limit, expiry |
| Media | `internal/media` | see "The media server" below — it forwards packets and stores nothing |

## What the server does not do

- **No recording, no transcription, no mixing to disk.** A recording is a custody decision about other people's
  voices and should not arrive as a side effect of a scheduling feature. The forwarder has no write path.
- **No whiteboard plaintext.** The room key is generated by the host's browser and travels **in the join link's
  URL fragment** (`#k=…`), which no browser sends to a server. Board events are opaque ciphertext; the API
  validates base64 shape and stores it. A late joiner replays the board by asking for everything after `seq`.
- **No card at the door.** A class is priced in **learning credits** only; `creditsCost: 0` is a free class.
  Credits are earned by studying (referrals, rewards, streaks) or **recharged for naira** through
  `POST /v1/wallet/topups` — ₦200 minimum, ₦10 a credit by default — and either way they land in the same
  append-only ledger, so a seat paid for with earned credits and one paid for with a top-up are indistinguishable
  at the door. What the room never does is take a card itself: that money path belongs to the wallet, with one
  idempotency rule instead of two.

## Fifty seats, and why the number is real

A peer-to-peer **mesh** costs each participant one uplink stream per peer. At fifty people that is fifty
uploads per phone, which no mobile connection carries — the old 8-seat ceiling was an honest description of a
mesh, not a policy choice.

The room is therefore forwarded by a media server (`apps/api/internal/media`, built on `pion/webrtc`):

- every participant holds **one** peer connection to the server;
- the host and up to five speakers publish; the server copies their packets to everybody who wants them;
- capacity is capped at **50** in validation *and* clamped at the door, so a row written by hand cannot admit
  the fifty-first person into a room the forwarder cannot carry.

What that costs, stated plainly:

- **Media is encrypted hop by hop, not end to end.** DTLS-SRTP protects participant → server and server →
  participant, but the server terminates both legs, so it can see the media. It does not record, and there is no
  code path that could, but that is a promise kept by the code rather than a property of the architecture. The
  whiteboard and chat keep their end-to-end property, because neither goes through the forwarder.
- **Uplink.** A full class with six publishers is roughly 6 × 400 kbit/s ≈ 2.4 Mbit/s of viewer downlink, and
  the server needs that per viewer in egress.
- **The stage is six seats, not fifty.** Fifty connections at 400 kbit/s each is more than a phone's downlink;
  a grid of fifty postage stamps is worse teaching than six faces plus a roster. Everybody else is in the room,
  visible on the roster, able to chat, and promoted into a slot when the host says so.

The connection's shape is fixed by the six stage slots: a slot holds a permanently bound audio and video track,
so promoting a speaker changes *which* publisher feeds a slot and never renegotiates anybody's connection
mid-sentence.

## The free-session limit

A free class (`creditsCost: 0`) is capped at **45 minutes**:

- at creation, a free class longer than 45 minutes is a `400` naming `durationMinutes`, and a free class with no
  stated length defaults to 45 (a paid class defaults to 60);
- at the door, `requireOpen` closes a free room whose session started more than 45 minutes ago — seating,
  joining, publishing and drawing all go through it. Merely refusing the caller would leave the seats and the
  stage open past the booking, so the class is ended and its attendance closed;
- on the clock, `CloseExpiredFree` runs every 60 seconds from the API process and closes free classes whose
  forty-five minutes are up. This is the half the door cannot do: a host who starts a free class and walks
  away never makes a request, so without the sweep the room stays `live` and the session row stays open. It
  is safe on every replica — the closing `UPDATE` is conditional on the class not already being ended, so
  concurrent sweeps converge instead of fighting — and a second sweep in the same minute closes nothing.

All three paths converge on one `closeRoom`, which ends the class, closes the open session, releases every
seat and asks the forwarder to drop the room's sockets. Three copies of that would be three chances to leave
a session row open. The paid-class exemption is part of the sweep's SQL rather than a check after the fact:
`TestAFreeClassClosesItselfWithoutAnyoneKnocking` starts a free class and a paid one, backdates both sessions,
runs the sweep, and asserts the free one is `ended` with no open session while the paid one is still `live`.

Paid classes run for the length their host booked, up to 480 minutes.

## Joining

`POST /v1/virtual-classes/{id}/join` performs everything that can race inside one transaction:

1. the class row is locked (`SELECT … FOR UPDATE` on PostgreSQL; SQLite serialises writers anyway);
2. an existing attendee row returns `200 alreadyJoined: true, creditsSpent: 0` — a double submit is not a
   second charge;
3. if the class requires approval and the caller is not the host, the transaction **stops here** with a
   `pending` attendee row: no seat, no charge, `202` (see *Admission and the waiting room* below);
4. capacity is clamped to at most 50 and counted after the lock, so exactly one of two people takes the last
   seat;
5. a discount code's `uses` is incremented with `max_uses` in the `WHERE` clause, so two simultaneous uses of
   the last one cannot both succeed;
6. the price is charged as a **negative ledger row** keyed `credits:virtual-class:<classID>:<userID>`, which is
   also what makes the charge idempotent;
7. the host is seated on stage in slot 0; everybody else starts as `audience` with slot `-1`.

A price is never trusted from the client. The host can only change the class's own price, and only while it is
not live.

## Admission and the waiting room

A class is created with one of two policies, and the policy is **fixed at creation** because flipping a room to
approval mid-lesson would turn out learners who are already inside:

| | `open` (default) | `approval` |
| --- | --- | --- |
| Joining | takes a seat, pays the price | creates a **request**: no seat, no charge, `202` + `pending: true` |
| Charged | at join | at acceptance, by the host |
| Access while undecided | — | roster, board, stage and signalling all answer `403`, naming why |
| Declined | — | `403` on every retry; the row stays so the learner is told rather than quietly re-queued |

Why charge at acceptance and not at the knock? Charging everybody who knocks means refunding every decline, and a
refund is a worse experience than a request: money leaves, then comes back a day later with a reference the learner
has to reconcile. Charging on acceptance means the only money that moves is money for a seat somebody actually got.

The host's side is two endpoints, both host-only in the service layer rather than hidden in the UI:

- `GET /v1/virtual-classes/{id}/requests` — the queue, oldest first, as full attendee records so the host's waiting
  room and the room's avatar list are the same objects;
- `POST /v1/virtual-classes/{id}/requests/{userId}` — `{decision: "accept" | "reject"}`. Accepting re-reads the
  price and the capacity **inside the class row lock** (the same lock a direct join takes), so accepts cannot
  oversell the last seat: the second one gets `409` and its request stays queued. A learner who is short of credits
  is refused with the number they are missing, and the request stays pending rather than being dropped — the host
  may still choose to admit them after a top-up.

A pending row is invisible to everybody but the host, and a rejected one never appears in a roster: a learner should
not be told who else was declined.

## The stage

`POST /v1/virtual-classes/{id}/stage` (host only) promotes a participant to `speaker` or returns them to
`audience`. Slots are allocated by the server from the lowest free one — a client asking for slot 3 is asking,
not deciding — and a demotion closes the participant's media session so their camera stops being forwarded
immediately rather than when the connection times out.

## Media negotiation

`POST /v1/virtual-classes/{id}/media` takes the browser's SDP offer and returns the forwarder's answer plus the
slot the server assigned. One request, one response:

- a publisher offers one audio and one video m-line to send on, then the stage's six video+audio receive pairs;
- an audience member offers only the receive pairs;
- the server's answer lines up one for one, which is why nothing is ever renegotiated.

A caller who is not seated gets `403`; the stage role comes from the attendance row, never from the request.

## Presence and attendance

A browser that crashes never sends a leave. Presence is therefore a heartbeat: an attendee is `present` while
`last_seen_at` is inside the 75-second window, and the signalling poll doubles as the heartbeat so there is no
separate ping endpoint. Attendance minutes are derived from the same rows, so the headline number in the host's
report is measured rather than asserted.

## The shareable link

A class has a 16-character slug drawn from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (32^16 possibilities, no
characters that are read aloud badly). `GET /v1/join/{slug}` is the one anonymous route: it answers what the
class is, who hosts it, how many seats it has and what it costs *before* asking for an account, and it does not
list the roster.

`joinUrl` is built from `EDUMART_WEB_URL`, so the link a host copies points at the deployment that issued it. The
host's "Copy link" appends `#k=<board key>`, which is how the board stays end-to-end encrypted while still
reachable from one shared URL.

## Consistency

`GET /v1/consistency` is the habit view: current streak, longest streak, and a per-day strip. It is **derived**
from activity the system already records — attempts started, live classes attended, credits earned — rather than
counted in a column, so it cannot drift from what happened. Days are UTC days and the payload says so.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `EDUMART_WEB_URL` | `http://localhost:3000` | Origin of join links and invitation links |
| `EDUMART_ICE_SERVERS` | one public STUN server | JSON array of iceServers (a hosted TURN service can be listed here) |
| `EDUMART_TURN_SECRET` | unset — relay off | Switches the self-hosted TURN relay on; also the key its credentials are signed with |
| `EDUMART_TURN_LISTEN_TCP` | same as `EDUMART_TURN_LISTEN` | TCP listener address, advertised as `?transport=tcp` once bound |
| `EDUMART_TURN_TLS_CERT` / `_KEY` | unset — plain TCP | Both together turn the TCP endpoint into `turns:`; one without the other is refused at boot |
| `EDUMART_TURN_PUBLIC_IP` | unset | The address clients are told to send to. Required when the secret is set, because a relay advertising an unreachable address is worse than none |
| `EDUMART_TURN_LISTEN` | `0.0.0.0:3478` | UDP address the relay binds |
| `EDUMART_TURN_REALM` | `edumart` | TURN realm; part of the credential hash |
| `EDUMART_TURN_TTL_MINUTES` | `60` | Lifetime of a minted credential |
| `EDUMART_MEDIA_UDP_MIN` / `EDUMART_MEDIA_UDP_MAX` | unset (OS picks) | UDP range pinned for the media forwarder, for a firewall that only forwards a few ports |
| `EDUMART_REFERRAL_RATES` | `10,3,1` | Commission percentage per referral level |

## NAT traversal

`GET /v1/virtual-classes/{id}/ice` returns the `RTCPeerConnection` iceServers list for **the caller**:

- the deployment's static `EDUMART_ICE_SERVERS` (a public **STUN** server by default), plus
- one `turn:` entry with a credential minted for that participant, when the embedded relay is enabled.

STUN alone connects most home networks. It cannot connect a network that blocks outbound UDP, or one behind a
symmetric NAT: the forwarder's address is unreachable and no direct path exists. Without a relay those learners
join the room, appear in the roster, and hear nothing — which is why the relay is part of the feature rather
than an operator's optional extra.

### The embedded relay

`EDUMART_TURN_SECRET` switches on a TURN server inside the API process (`internal/relay`, built on
`pion/turn`). It binds UDP **and TCP on the same port**, optionally TLS
(`EDUMART_TURN_TLS_CERT` + `EDUMART_TURN_TLS_KEY` turn the TCP endpoint into `turns:`), allocates relay ports on
the public address, and authenticates with the
[TURN REST scheme](https://datatracker.ietf.org/doc/html/draft-uberti-behave-turn-rest-00): the username is
`<unix expiry>:<user id>` and the password is `base64(HMAC-SHA1(secret, username))`. Three properties are the
point:

1. **No shared password ships to a client.** A bundle with a permanent TURN password leaks one the first time a
   browser caches it, and every user shares the leak.
2. **Credentials expire.** A scraped username/password stops working when the window closes (default one hour),
   so abuse is a short ride rather than an open relay.
3. **Credentials are attributable.** The user id is inside the value the server recomputes the password from, so
   the relay keeps no session table and abuse still traces to an account.

The secret never reaches a client; hosts do not see other participants' credentials; the list is rebuilt per
request with a fresh expiry rather than stored. Everything the relay is asked to do is checked by the library's
own REST auth handler, and the tests assert **both** directions: a minted credential allocates, a tampered or
expired one is refused, and a packet written through the allocation comes back.

Because a credential is derived from the shared secret rather than stored, **every replica can serve every
participant**: a fleet of API pods behind one UDP load balancer needs no sticky sessions, and a credential minted
by one pod is accepted by the next. That falls out of holding no session table, which is the same property that
makes abuse attributable.

Two deployment facts follow from the protocol and are not optional:

- **The UDP port must be reachable from the internet.** In Kubernetes the API Service is `ClusterIP`, so a
  deployment either adds a UDP `LoadBalancer`/`NodePort` on 3478 or points `EDUMART_ICE_SERVERS` at a hosted
  relay instead. Nothing in this repository runs a cluster yet.
- **The forwarder's own UDP ports must be open too.** On a firewalled host pin `EDUMART_MEDIA_UDP_MIN`/`MAX` and
  forward that range.

## Referral levels

Commission is paid up the referral chain, one ledger row per level, each with its own rate and its own
idempotency key (`commission:referral:<orderID>:L<level>:<userID>`):

- the chain is walked from `referral_attributions` → `referral_codes.owner_user_id`, one hop per level;
- a refund reverses **every** level proportionally (`commission:reversal:<refundID>:L<level>`);
- a cycle stops the walk instead of paying around it;
- `GET /v1/referrals/tree` reports each rung's count, qualifications and actual paid commission.

Students, tutors and institutions all participate: `accountType` at signup is intent used for onboarding, and
it changes nothing about who may refer or be referred.

## What is not built

- **No hosted relay and no bandwidth accounting.** The embedded relay speaks `turn:…?transport=udp`,
  `turn:…?transport=tcp` and — with a certificate — `turns:…?transport=tcp`, so a network that blocks UDP is served
  by the TCP endpoint. An endpoint is advertised only when its listener actually bound (`relay.URLs`), because a URL
  for a closed port makes a browser spend its budget on a path that cannot work. Allocations are bounded by
  credential lifetime, not by a per-user quota, and CI does not open a real TLS listener — the certificate path is
  covered by the "TLS needs a key too" test, not by a handshake against a public hostname.
- No relay accounting: allocations are bounded by credential lifetime, not by a per-user bandwidth quota.
- No recording, transcription or captions.
- No mobile video room: the mobile app lists classes and sittings and opens the link; the room itself is the web
  app, so there is one implementation of the board's key rather than two that disagree.
- The stage is six seats. Larger panels are a product change (a second stage row would double the downlink), not
  a config flag.
